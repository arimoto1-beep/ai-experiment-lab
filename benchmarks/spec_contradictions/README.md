# 仕様書の矛盾検出ベンチマーク v1

Haiku 5.5 / medium、Haiku 5.5 / max、Opus 4.8 / high の運用設定を比較する。純粋なモデル能力のランキングではない。
既存のPython課題とその隠しテストは使用・変更しない。実行は `python -m ai_lab.spec_benchmark`、採点は `ai_lab/spec_scoring.py` で行う。

## 課題と固定データ

| 仕様書 | 要件数 | 矛盾のID集合数 | うち重大 | 情報不足の項目数 | 誤検出対照のID集合数 |
|---|---:|---:|---:|---:|---:|
| `order_fulfillment`：受注・出荷 | 20 | 4 | 1 | 2 | 4 |
| `expense_approval`：経費申請・承認 | 20 | 4 | 3 | 2 | 3 |
| `access_control`：会員・権限管理 | 20 | 4 | 3 | 2 | 3 |

本文は `specs/`、非公開の正解は `answer_keys/` に分ける。正解データは、矛盾の最小ID集合・理由・重大度、情報不足と不足情報、矛盾しない対照例、正常要件のIDを含む。
各課題は、直接の矛盾3件と3要件を組み合わせる矛盾1件を含む。条件の違いと明示的な例外を本文に書き、ID順の優先順位、推測による例外、業務常識による補完を認めない。
v1の6入力ファイルのSHA256を `manifest.json` に固定している。ロード時に不一致なら実行しない。実験開始後はロードした本文・正解だけを使い、原本を再読込しない。
入力6ファイルは `.gitattributes` でLF改行に固定し、Windowsのcheckoutによる改行変換でハッシュが変わらないようにする。
実験条件には入力とプロンプトのハッシュを保存し、`snapshots/` に本文と正解を保存する。これらのスナップショットは採点・再確認用で、モデルの作業場所にはコピーしない。
問題や正解を改訂する場合は別のデータ版として扱い、既存の実験と同一条件とみなさない。実験中の問題・正解の編集は禁止する。

重大度は採点前に固定する。本課題での `critical` は、出荷・支払の必須前提を満たせない、支払承認統制が成立しない、会員のアクセス制御・個人情報・監査ログの保持方針が両立しない問題とする。
`major` はキャンセル可否、送料・通貨・追跡番号の項目値、招待リンクの期限の不一致とする。今回は `minor` に分類する正解はない。
モデルが重大度を回答しても、重大な見落としの計算には固定した正解側の重大度だけを使う。

## 正解の妥当性確認

`tests/test_spec_ground_truth.py` は本文の意味から独立に書いた具体的条件の制約を使う。
各矛盾の有限状態を列挙し、すべての要件を同時に満たす状態がないこと、任意の1要件を外せば満たせることを確認する。これにより3要件の矛盾を不適切な2要件だけで正解としない。
条件の異なる対照例と明示的例外は、該当条件ごとに両立する状態があることを確認する。
情報不足は、本文と両立する2通りの情報補完で業務判断が変わることを確認する。例えば「長期間」は7日と30日のどちらでも本文に適合し、出荷10日後の判定が変わる。
ID参照、重複、重大度、全要件の分類、入力ハッシュも自動確認する。
有限状態による確認は、日本語のあらゆる解釈を機械的に証明するものではない。本文と正解理由の照合も必要である。しきい値・対象条件・同一フィールド・例外を本文で明示し、実在の法制度や未指定の業務規則に依存する採点は除いた。

## 回答と採点規則

モデルには本文と回答形式だけを渡す。回答はJSONオブジェクト1つとする。

```json
{
  "contradictions": [
    {"requirement_ids": ["Rxx", "Ryy"], "reason": "同じ条件で両立しない理由"}
  ],
  "insufficient_information": [
    {"requirement_ids": ["Rxx"], "reason": "判断に不足する情報"}
  ]
}
```

上のIDは書式の説明であり、実際には本文のIDを使う。`contradictions` は必須、`insufficient_information` は任意。理由は空でない文字列が必要。情報不足は矛盾の採点から除外し、別に保存する。

- IDの順序を無視した集合の完全一致で、TP・FP・FNを数える。不要なIDを足した集合はFPで、対応する正解はFNになる。
- 3要件が必要な矛盾を2要件だけで報告した場合もFP・FNになる。同じID集合の重複報告は1件にまとめ、重複件数を記録する。
- Precision = TP / (TP + FP)、Recall = TP / (TP + FN)、F1はその調和平均。正解も回答も空ならすべて1。正解があるのに回答が空ならすべて0。正解が空で誤検出があればPrecision=0、Recall=1、F1=0。
- 重大な見落としは、FNとなった正解のうち `critical` の件数。
- JSON不正、Markdown付き回答、JSONキー重複、NaN、未知ID、IDの重複、空の理由、スキーマ不正、CLI異常を記録する。回答全体を採点不能としてTP=0・FP=0・FN=全正解、Precision/Recall/F1=0にする。正解が空でも形式不正を正解にしない。
- ID集合が一致しても、理由が正しいとは判定しない。`reason_review.json` にモデル理由、正解理由、ID判定、期待重大度、未記入の `reason_verdict` と `review_note` を保存する。別途人が理由を確認する。情報不足の理由も同じファイルに保存する。

集計は仕様書別と全体を表示する。microのPrecision/Recall/F1は合計TP/FP/FNから計算する。`mean_F1` は形式不正を0点として含む試行ごとのF1平均。
形式不正のFPは抽出不能なので0として数える。必ず `invalid` と平均F1も併せて比較する。正解0件の課題は採点テスト用の模擬データで検証し、4種類目の公開課題は追加していない。
指定モデルと実モデルの不一致・実モデル未確認は別に数え、その試行を指定モデルの成績として解釈しない。
同じ仕様書の入力ハッシュが異なる実験を同じレポートに指定した場合は、比較を拒否する。

## 正解データの隔離

既存のサブスクリプション認証確認と従量課金用環境変数の除去を再利用する。
各試行は新しい空の一時ディレクトリで、`--no-session-persistence` を付けて独立実行する。
`--tools ""` で組み込みツールを無効にし、`--disallowedTools "*"` でMCPを含めて全ツールを拒否する。`--safe-mode` でCLAUDE.md・スキル・通常のフック・MCPなどのカスタマイズの自動読込を無効にする。
正解ファイルの内容・パス・件数や採点結果をプロンプトに入れず、ファイルを読む手段も渡さない。
この隔離はClaude Codeのツール制御による。OSの別ユーザーやコンテナによる隔離ではない。管理ポリシーのフック等はsafe modeでも適用されるため、実機の管理設定については別途確認が必要。
フラグの根拠は[Claude Code公式CLIリファレンス](https://code.claude.com/docs/en/cli-reference)（2026-10-11確認）。実モデルは開発中に呼び出していない。

## 実行

まずデータだけを検証する。

```powershell
python -m ai_lab.spec_benchmark validate
python -m pytest
```

次の3条件のコマンドは、各仕様書を3回、計9回ずつ実行する。最初は末尾に `--dry-run` を付け、モデルを呼ばずに条件と固定データを確認する。実実験は独立したPowerShellターミナルで行う。

```powershell
python -m ai_lab.spec_benchmark run --spec all --model haiku --effort medium --runs 3
python -m ai_lab.spec_benchmark run --spec all --model haiku --effort max --runs 3
python -m ai_lab.spec_benchmark run --spec all --model opus48 --effort high --runs 3
```

1仕様書だけなら `--spec order_fulfillment` 等を指定する。`--timeout`、`--results-dir`、`--claude-bin` も指定できる。Haiku 5.5は既存READMEのとおりClaude Code 2.1.293以上を使う。
出力された実験ディレクトリを指定して比較する。

```powershell
python -m ai_lab.spec_benchmark report "results\<mediumの実験フォルダ>" "results\<maxの実験フォルダ>" "results\<opus48の実験フォルダ>"
```

各 `trial_NNN/` に `answer.txt`、CLIの生出力、`trial.json`、`reason_review.json` を保存する。
`trial.json` は課題名・モデル照合・Effort・実行時間・トークンとキャッシュ使用量・API換算費用・CLI報告費用・採点・エラーを含む。`summary.json` は試行ごとに更新し、中断しても完了済みの記録を残す。
料金は既存の計算を再利用し、CLI報告料金と区別する。TTLが不明な場合は1時間の単価を仮定する。Haikuの長文料金等の既存の制約は `cost.notes` とリポジトリREADMEを参照する。
